## Phase 1 — `zbrain sync`

**Status: done.** `src/core/git-sync.ts` + `src/commands/sync.ts`, registered in `src/index.ts`. Tests: `tests/sync.test.ts` (5 tests, all pass) + manual CLI smoke (two-machine round trip via a real bare repo).

Deviations / decisions not spelled out in the plan:

1. **Used `node:child_process.spawnSync`, not `Bun.spawnSync`.** The plan sketch said `Bun.spawnSync`; `src/commands/helpers.ts` already shells out via `node:child_process.spawnSync` (see `checkQmdInstalled`). Matched existing convention instead of introducing a second way to shell out.

2. **Explicit branch name for pull/push, not bare `git pull --rebase` / `git push`.** The plan's sketch used plain `git pull --rebase` / `git push`. In practice, a brand-new local repo has no upstream tracking branch configured, so a bare `git push` fails with "no upstream branch" and a bare `git pull --rebase` fails with "no tracking information" — this would make the *very first* sync on a fresh clone always error, which is the opposite of the self-healing behavior the plan wants elsewhere (`ask` auto-heals a stale index). Fixed by resolving the current branch via `git rev-parse --abbrev-ref HEAD` and always calling `git pull --rebase origin <branch>` / `git push -u origin <branch>` explicitly. `-u` is idempotent (a no-op once tracking is already set), so this is safe on every subsequent sync too.

3. **First sync against an empty remote is not an error.** A brand-new bare repo has no ref for the branch yet, so `git pull --rebase origin <branch>` fails with `couldn't find remote ref <branch>`. This is expected on a team's very first sync, not a conflict — detected by matching that string in stderr and downgraded to a warning (`remote has no "<branch>" ref yet (first sync)`) instead of throwing.

4. **`initGitWorkspace` seeds a `.gitignore` file.** Git does not track empty directories. A freshly-scaffolded workspace only has empty `wiki/<tier>/` directories, so without at least one real file, `HEAD` stays "unborn" (no commits possible) and the first `sync` has nothing to rebase onto — `git rev-parse --abbrev-ref HEAD` errors on an unborn branch. Discovered via a failing test (`ambiguous argument 'HEAD': unknown revision`). Fixed by writing an empty-ish `.gitignore` during `sync init`, guaranteeing a trackable file exists so the first commit always succeeds. Per the plan's own instruction, nothing is excluded by default — `.trash/` is intentionally included so `forget` propagates to the team.

5. **Rebase conflicts are never auto-resolved.** On `git pull --rebase` failure that isn't the "empty remote" case, the code runs `git rebase --abort` and throws with the workspace path + a pointer to re-run `zbrain sync` after manual resolution — per the plan's "never auto-resolve" rule and the supersede-model rationale (conflicts should be rare because updates create new notes rather than editing in place).

6. **Commander subcommand ambiguity check.** `zbrain sync <workspace>` (direct action) and `zbrain sync init <workspace>` (subcommand) coexist on the same parent command. Verified with a standalone commander script that `sync team` and `sync init team` both dispatch correctly — commander matches subcommand names first, then falls back to the parent's own argument+action. Edge case not handled: a workspace literally named `init` would be unreachable via `zbrain sync init` (it would always be interpreted as the subcommand). Not worth a workaround at MVP scale — flagging here so it's a known, accepted tradeoff rather than a silent gap.

7. **Full reindex on every sync, not incremental.** The plan explicitly allowed this ("Full rebuild is fine at MVP scale"). `rebuildWorkspace` diffs file `content_sha` against DB rows, so it's cheap for the workspace sizes a small team will have; revisit only if `doctor`/`sync` latency becomes noticeable.

## Phase 2 — Fast-path note add

**Status: done.** `zbrain note add` (CLI) + `add_note` (MCP) both wired to the existing `createNote`/`detectConflict`/`upsertNote` primitives — no new core logic needed, just orchestration. Tests: `tests/note-add.test.ts` (5) + 2 new cases in `tests/mcp-protocol.test.ts`, plus the `tools/list` count bumped 4→5.

Deviations / decisions not spelled out in the plan:

1. **Body resolution mirrors `learn.ts`'s existing pattern exactly** (`--body` → `--file` → stdin-if-non-TTY → interactive prompt), rather than inventing a new convention. Consistency over novelty — this repo already has one way to "get text into a command."

2. **`note add`'s slug defaults to `slugify(title)`,** matching the tier/slug/title shape `createNote` already expects. No new slugging logic was written; `slugify` was already exported from `note-service.ts`.

3. **Found and fixed a real pre-existing bug while touching `note.ts` (in scope per the plan's own §2.2 note).** `runNoteUpdate` called `detectConflict(paths, ws, tier, options.slug ?? found.tier, [])` — when no `--slug` was passed, it fell back to passing the **tier string** ("axioms") as the **slug** argument, so it was checking for a conflict at the wrong path (`axioms/axioms.md` instead of the note's real path) or worse, silently allowing a real conflict through. Fixed by only running `detectConflict` when `--slug` is explicitly provided (the auto-generated slug is UUID-derived and can never collide, so skipping the check when unset is correct, not a shortcut). Added a regression test (`note update: only checks conflict when --slug is explicitly passed`).

4. **Removed the dead `findNoteById` stub** (lines 27–31 of the old `note.ts`) — it returned a placeholder object and had zero call sites; `locateNote` (further down the same file) is the function actually used everywhere. Straightforward dead-code deletion, not a refactor of anything working.

5. **MCP `add_note` conflict errors surface the existing note's id in the message**, not just a generic "conflict" — so an agent hitting a conflict can immediately call `get_note` on that id to decide whether to supersede, without a second round-trip to discover it. Same pattern applied to the CLI's error message.

6. **`--source <id...>` CLI flag uses commander's variadic option syntax** to accept zero or more evidence source ids, mapped to `sources` in the options object before calling `runNoteAdd` (commander names variadic options after the flag, i.e. `options.source`, not `options.sources` — renamed at the call site to match the function's parameter name).

7. **Asset updates were the minimum needed to describe the new command**, not a rewrite of the engine rules: added one row to the `claude-rules.md` skill-trigger table + one short "Fast path" paragraph in the Evidence Pipeline section, and a matching bullet in `codex-rules.md`'s Expected Usage list (that file already uses plain bullets, not a table, for the same content). Regenerated `src/generated/bundled-assets.ts` via `bun run generate:assets` per `CLAUDE.md`'s explicit instruction to do so after any `assets/` change.

## Phase 3 — Sessions table

**Status: done.** `touchSession`/`listStaleSessions`/`deleteSession` added to `src/core/session.ts`; wired into `zbrain ask` and MCP `recall`; `checkIdleSessions` in `src/core/doctor.ts` is now a real check (was a permanent no-op stub) plus a new `fixIdleSessions` used by `zbrain doctor --fix`. Tests: `tests/session-db.test.ts` (6, new file) + 3 new cases in `tests/doctor.test.ts`.

Deviations / decisions not spelled out in the plan:

1. **`checkIdleSessions` and `listStaleSessions` gained an optional `workspace` filter** the plan's sketch didn't include (`listStaleSessions(db, idleDays)` with no workspace param). `runDoctor` already loops per-workspace and reports 8 checks per workspace call, so an unfiltered idle-session check would report every idle session under every workspace's output — misleading duplication. Filtering by the `workspace` column (which the `sessions` table already had) keeps idle-session reporting consistent with every other doctor check.

2. **Scoped down the "file-without-row" orphan backfill from the plan.** Plan §3.3 said: *"flag orphans (row without file / file without row)... file-without-row is expected pre-migration, so `--fix` backfills rows from file mtime instead of deleting."* This isn't actually possible as specified: `project_root` is stored in the DB as a plain string, but the on-disk session directory name is `sha256(project_root).slice(0,16)` — a one-way hash. Given only the directory hash, the original `project_root` string cannot be recovered, so a backfilled row would need a fabricated `project_root` that could never match a real project's hash again (useless for future `touchSession` upserts or lookups). Implemented `--fix` for the two cases that are actually safe: idle stale-row GC (delete row + file) and "row survives but is idle" — both have everything needed to act correctly. Did not implement the row-without-file / file-without-row cross-check at all this phase; flagging here rather than silently dropping it, since it's an explicit (if underspecified) plan item.

3. **`--fix` runs once per workspace before the report loop**, not as a flag threaded through `runDoctor` itself. `runDoctor(paths, workspace, db)` stays a pure read-only report generator — existing test `runDoctor: full report on clean workspace` asserts `report.results.length === 8` and iterates checks without expecting side effects; keeping it pure avoids retrofitting an options object through a function that has callers besides the CLI. The CLI (`src/commands/doctor.ts`) calls `fixIdleSessions` directly per workspace when `--fix` is passed, then runs the normal (now-clean) report afterward so the user sees the post-fix state.

4. **MCP server gets one `sessionId` for its whole process lifetime** (`getSessionId()` called once in a class field initializer), not one per tool call. Rationale mirrors the existing comment in `ask.ts` about per-session context files: a single Claude Code session talks to one long-lived MCP server process via stdio, so the session id should stay stable across every `recall` call in that process, the same way `ZBRAIN_SESSION_ID` stays stable across multiple `zbrain ask` invocations in one shell session.

5. **`touchSession` is only called from `recall`, not from every MCP tool.** Plan explicitly scoped this to "`ask.ts` and MCP `recall`" — `add_note`/`remember`/`get_note`/`list_pending` don't represent "retrieval activity" the way `ask`/`recall` do, so touching the session on those would inflate `last_activity_at` for actions that aren't really evidence of an active retrieval session. Kept to the plan's exact scope.

## Phase 4 — Kill `projects.json` mirror

**Status: done.** SQLite (`projects` table via `readProjectBinding`/`upsertProjectBinding`) was already the actual resolution path in code (`workspace-resolver.ts`) — `projects.json` was a write-only mirror nothing in `src/` ever read back. Removed the write in `initProject` (`src/commands/helpers.ts`), added a one-time import-then-archive migration in `initDb` (`src/core/db.ts`), added `zbrain workspace current` (`src/commands/workspace.ts`), and updated every asset/doc that told an agent to read the file directly. Tests: `tests/registry-migration.test.ts` (5, new file). `grep -rn "projects.json" src/ assets/` now only matches the migration code itself and one comment — confirmed after the change.

Deviations / decisions not spelled out in the plan:

1. **Migration lives in `initDb()`, not in `runSetup`/`assertRuntimeReady`.** Plan §4.3 step 3 said "one-time migration in `runSetup`/`assertRuntimeReady`," but neither of those functions has DB access at the point they run (`assertRuntimeReady` only checks `existsSync`; every command calls `initDb` separately afterward). `initDb(runtimeDir)` is the one function every code path already calls before touching the `projects` table, and it already owns schema bootstrap/migration — a legacy-data import is the same category of "make the DB correct before anyone queries it" work. Placing it here also means the migration runs exactly once per fresh `~/.zbrain` regardless of which command happens to run first (`ask`, `init`, `doctor`, etc. all call `initDb`), rather than being coupled to `setup`/`init` specifically.

2. **Migration is naturally idempotent via the rename, not a flag.** After the first successful run, `projects.json` no longer exists (renamed to `.bak`), so `existsSync(registryFile)` short-circuits on every subsequent `initDb` call. No separate "have I migrated" marker needed.

3. **Existing SQLite rows always win over the legacy file.** For each legacy entry, `readProject(db, project_root)` is checked first; only import if the DB is missing. Protects a fresh SQLite write (e.g. from a `zbrain init` that ran in the same window as an old `projects.json` sitting on disk) from being clobbered by stale JSON. Verified with a regression test that seeds a fresher SQLite row and confirms it survives the import.

4. **Malformed legacy `projects.json` is archived, not left in place or deleted.** If `JSON.parse` throws, the import step is skipped (nothing to import) but the file is still renamed to `.bak` — matches the Hard Rule (never destroy files outright) while still guaranteeing the stale/broken file is out of every future `existsSync` check.

5. **`zbrain workspace current` always prints JSON — dropped the `--json` flag the plan's command sketch showed.** Plan text said "Plain stdout JSON (this one is machine-read; keep clack for human paths only)" — i.e. there was never going to be a non-JSON output mode for this command, so a flag that's always a no-op would be confusing rather than useful. Implemented as `zbrain workspace current` with unconditional JSON output; a pure `resolveWorkspaceCurrent(paths)` helper was factored out of the CLI action specifically so the resolution logic (not just its stdout side effect) is directly unit-testable, matching how `runNoteAdd`/`runAsk` already separate "core result" from "how it's displayed."

6. **Updated the checked-in root `CLAUDE.md` in addition to `assets/`.** Not explicitly listed in plan §4.3.1 ("update every asset... engine rules, skills"), but this repo's own `CLAUDE.md` documents the exact same workspace-resolution order in prose (`### Workspace and Project Pointer`) and also contains a stale injected copy of the old `assets/engine/claude-rules.md` content (from a previous `zbrain init` dogfooding run, predating even Phase 2's `note add` addition). Left the Phase-2-era drift in that injected block alone (out of scope for this phase) but fixed the `projects.json`-specific lines in both places — leaving factually wrong architecture docs in the project's own guidance file would undercut the whole point of this phase.

## Phase 5 — Docs + release

**Status: done.** README "Team setup" section, `CHANGELOG.md` v2.1.0, `AC-AUDIT.md` (AC-P1-9 flipped to ✅), full gate (`bun run typecheck && bun test && bun run build`), and a hand-run binary A→B→A sync round-trip via `ZBRAIN_HOME`-isolated smoke homes + a local bare git remote.

**A real bug was found and fixed during the smoke test, not just documented.** The plan's own "one full A→B sync round-trip by hand" step exists precisely to catch this class of gap, and it did:

1. **`zbrain sync init <ws> --remote <url>` never supported joining an already-populated remote.** `initGitWorkspace` always ran a plain `git init`, so when a second teammate pointed it at a remote that already had commits (from the first teammate's `sync`), the two histories were unrelated. The first `sync` then tried `pull --rebase` and conflicted immediately on the seeded `.gitignore` — reproduced with the actual compiled binary, not just unit tests. Root cause was confirmed by finding that `tests/sync.test.ts`'s own "Home B" scenario never actually called `initGitWorkspace` for the joining side — it did a raw `git clone` instead, with a comment admitting it "simulates a teammate's first checkout." The public CLI path was never exercised.
2. **Fix, scoped to `src/core/git-sync.ts`:** `initGitWorkspace` now does `git fetch origin` right after `remote add`, checks for an existing `origin/main` or `origin/master`, and if found runs `git clean -fd` (to clear the just-scaffolded, untracked starter files — `workspace.md`, `evidence/_index.md`, `.zbrain-layout-version` — that would otherwise block the checkout) followed by `git checkout -B <branch> origin/<branch>`. Only when no existing remote branch is found does it fall through to the original "seed `.gitignore`, let the first `sync` create the initial commit" path. This was presented to the user as a choice (fix vs. document-the-manual-workaround vs. defer) via `AskUserQuestion` before implementing, since it touches Phase 1 code already marked complete — user chose "fix it."
3. **Added `tests/sync.test.ts:"initGitWorkspace: joining a workspace whose remote already has history adopts it instead of diverging"`**, which exercises the real CLI path (`initGitWorkspace` directly, no manual `git clone`) and asserts the joining side sees the first teammate's note on disk immediately, with no rebase conflict on first `sync`. `makeHome()` was upgraded to scaffold the same untracked starter files real `workspace create` writes (previously it only made empty tier directories), specifically so this test would have caught the untracked-file collision the first version of the fix still had — it did, on the first binary-level smoke run, before the unit test alone would have surfaced it.
4. **First test-writing pass got the assertion path wrong**, asserting `wiki/axioms/from-a.md` doesn't exist under `<ws>/axioms/...` — corrected to `<ws>/wiki/axioms/...` per the V2 layout migration (`<ws>/<tier>/` → `<ws>/wiki/<tier>/`, documented in the 2.0.0 changelog entry). Not a logic bug, a path bug in the new test.
4a. **Follow-up `/check` review caught a critical data-loss bug in fix #2 above, before anything was committed.** The first version of the fix ran a blanket `git clean -fd` whenever an existing remote branch was found, on the assumption that the only untracked files present would be the 3 known scaffold placeholders. That assumption breaks if a teammate had already been using the workspace locally (writing real notes via `learn`/`note add`) *before* deciding to turn it git-backed and point it at a remote that happens to already have history — `git clean -fd` would silently delete every one of those untracked real notes with no recovery path (nothing was ever committed, so there's no git history to recover from). Fixed by auditing `git status --porcelain --untracked-files=all` (which lists every individual untracked path, unlike `git clean -n`'s directory-collapsing output — `git clean -n` alone would print an indistinguishable `Would remove wiki/` whether that directory is empty scaffold or full of real notes) and refusing to proceed if anything beyond the 4 known-safe scaffold paths (`workspace.md`, `evidence/_index.md`, `.zbrain-layout-version`, `.gitignore`) is present. A second follow-on bug was caught in the same review pass: the refusal path left behind the `.git` directory `git init` had already created before the safety check ran, so the error message's own suggested recovery ("move it aside, then re-run `sync init`") would have failed with "already a git repo" on retry — fixed by `rmSync`-ing the just-created `.git` dir before throwing, verified with a test that the exact suggested recovery flow (move the conflicting note aside, re-run) succeeds. Added `tests/sync.test.ts:"initGitWorkspace: refuses to join and discard a workspace that already has real local content"` and reproduced both the original bug and the fix at the compiled-binary level (real pre-existing note survives the refused join; retry after moving it aside succeeds).
5. Documented in README's "Team setup" section that leases/optimistic-locking are same-machine-only protection; cross-machine consistency is git's job via the supersede-not-overwrite lifecycle plus ordinary git conflict resolution on markdown files if two machines ever collide on the same path.
6. `AC-AUDIT.md` summary counts updated: P1 10/10 closed (was 9/10), overall 21/23 closed / 2 partial (was 20/23 / 3 partial) — the remaining 2 partials (`AC-P2-4` dead-code cleanup, `AC-P3-2` UUID-not-ULID) are unrelated to this plan and intentionally untouched.

**Verification:** `bun run typecheck` clean; `bun test` → 108 pass / 0 fail / 337 expect() calls across 18 files (up from 107, +1 for the new join-adoption test); `bun run build` → `dist/zbrain` compiles.

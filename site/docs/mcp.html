MCP gateway

The shipped binary is standalone and Go-native. It includes the local integration surfaces described in docs/trusted-agent-gateway-spec.md: the stdio gateway, the local owner ceremony, and the loopback viewer. All three surfaces reuse workspace boundaries and fail-closed trust validation; canonical Markdown and immutable evidence remain the trust inputs.

zbrain mcp serve

Run the MCP stdio gateway. stdout is protocol-only; diagnostics go to stderr.

The gateway serves the trusted-agent MCP gateway over stdio. Protocol frames stay on stdout and diagnostics stay on stderr. Help output, verbatim:

Usage: zbrain mcp serve

Serve the trusted-agent MCP gateway over stdio.
Usage: zbrain mcp serve

Run the MCP stdio gateway. stdout is protocol-only; diagnostics go to stderr.

The gateway operates on the same workspace boundaries as the CLI: the runtime root configured by ZBRAIN_HOME or the default ~/.zbrain/. Canonical Markdown and immutable evidence remain the trust inputs; raw evidence is not indexed or treated as trusted instructions.

The gateway exposes these tools:

  • memory_reindex

    Rebuilds the workspace index over MCP. Exposes the same embedding opt-in as embedding: true; the default is false.

  • memory_ask

    Returns trusted context JSON over MCP. Exposes the same embedding opt-in as embedding: true; the default is false.

  • claim_lifecycle

    The tool through which an agent requests a lifecycle transition. It applies the mutation itself; no HTTP endpoint does.

Approval ceremony

An agent requests a lifecycle transition through the MCP claim_lifecycle tool; the local owner approves it. The agent receives a one-time grant token, and the gateway, not an HTTP endpoint, applies the mutation.

This is the owner-pinned lifecycle described in docs/trusted-agent-gateway-spec.md. The ceremony takes four steps:

zbrain approval show <challenge-id>
zbrain approval grant <challenge-id>
  1. prepare binds the workspace, operation, claim ID, canonical draft digest, superseded IDs, prior verification digest, and revoke reason, then returns a challenge ID, action summary, and SHA-256 action digest.
  2. The owner runs zbrain approval show <challenge-id> to inspect the bound action.
  3. In an interactive TTY, the owner runs zbrain approval grant <challenge-id>, confirms the final 16 hexadecimal digest characters, and receives the one-time token.
  4. The agent calls claim_lifecycle with apply and the challenge ID/token; the gateway revalidates the workspace, token, expiry, and current canonical state under the workspace lock before applying the transition.

The two owner commands, verbatim from their help output:

Usage: zbrain approval show <challenge-id>

Print the challenge action summary as JSON.
Usage: zbrain approval grant <challenge-id>

Confirm the last 16 hex characters of the action digest in an interactive
TTY, then verify and print the one-time token as JSON for later apply.

The gateway is launched per use with zbrain mcp serve; there is no background service, and MCP is stdio-only.

Timing and replay facts:

  • Challenge

    Valid for 15 minutes from preparation. prepare emits no plaintext token.

  • Grant token

    The owner grant issues one with its own lifetime of up to 5 minutes, capped by the challenge expiry. The grant step records owner approval without consuming the token; apply atomically consumes it once.

  • Replay

    Replay of a consumed token, an expired challenge or token, a mismatched digest, workspace, or claim, and a stale canonical draft all fail closed; the agent must prepare a fresh challenge rather than retrying a stale action.

This is the owner-pinned ceremony: prepare emits no plaintext token, the owner grant issues the one-time token, and apply consumes it once under the workspace lock.

zbrain view

The loopback-only read-only viewer via zbrain view serves an embedded viewer on 127.0.0.1 only. Help output, verbatim:

Usage: zbrain view

Serve the embedded read-only viewer over loopback (127.0.0.1).

The viewer binds loopback only, sends strict CSP and nosniff headers,
has no CORS, and returns 405 for every method other than GET and HEAD.

The viewer is read-only: it only reads workspace state, and its strict header policy leaves no room for embedding or cross-origin calls.

Optional hybrid retrieval

Lexical retrieval is the default for both the CLI and the MCP gateway. Hybrid retrieval is an explicit opt-in, never the default:

The behavior, verbatim from the README:

Lexical retrieval is the default for both the CLI and the MCP gateway. Pass
--embed to zbrain ask to opt into local hybrid retrieval, and use
zbrain reindex --embed to build the local loopback embedding sidecar. The MCP
memory_reindex and memory_ask tools expose the same opt-in as
embedding: true; their default is false. Embedding work is local-only and
never calls a network service. If the sidecar is missing or empty, an
embedding request falls back to lexical results instead of failing or
changing trust semantics.

  • CLI

    Pass --embed to zbrain ask to opt into local hybrid retrieval, and use zbrain reindex --embed to build the local loopback embedding sidecar.

  • MCP

    The memory_reindex and memory_ask tools expose the same opt-in as embedding: true; their default is false.

  • Local-only

    Embedding work is local-only and never calls a network service. If the sidecar is missing or empty, an embedding request falls back to lexical results instead of failing or changing trust semantics.

All gateway surfaces preserve the fail-closed runtime contract: ask fails closed for dirty, missing, stale, or rejected indexes, and claim_lifecycle apply revalidates workspace, token, expiry, and canonical state before mutating. MCP is stdio-only; there is no remote or HTTP MCP transport.
